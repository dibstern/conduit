Composer redesign: goal, harness, and controls

Fourteen designs for the new message composer, plus three designs for the combined Harness & Model picker, a full goal lifecycle, and the OpenCode story. Phones are 390px wide and a fixed height, so every pixel the composer takes is honest. Everything is clickable where it says so: effort cycles, menus open.

What must fit

Goal, always visibleWhen a /goal is active you can see what it is, how it's going, and why it isn't done yet. You can edit or clear it in one tap.
Live statusFrom B3: working time, the current step, and a jump back to live. Stop is always one tap away.
Harness & Model buttonOne button showing the harness logo and model name. It opens harness, model, effort, context window, and agent. The standalone agent and context-window selectors go away.
Effort, quickChanging effort takes one tap, without opening the picker.
Approvals, quickOne tap away, amber when elevated. It opens a menu rather than cycling, so you can't land on Full access by accident.
AttachFiles, photos, and camera, plus @ files and / commands. Setting a goal also lives here.

What a goal actually is

Researched against the Claude Code docs (code.claude.com/docs/en/goal) and the installed SDK 0.3.280.

HarnessNative goal?What a UI can read
ClaudeYes. /goal <condition>, /goal for status, /goal clearactive_goal message: condition, iterations (turns checked), set_at, tokens_at_start, last_reason. null when cleared. After each turn a small model decides not yet, met, or impossible. Catch: the type is not in the public query() union, so we need to verify at runtime that we receive it.
OpenCodeNo. Request #27167 is open. Only community plugins exist.Nothing native. See OpenCode for options, including conduit running the goal loop itself.
Codex (precedent)Yes, plus pause / resumeNot a conduit harness. It's the reason pause shows up in one design.

So the goal UI has these fields to show: condition, elapsed, checks, tokens, last reason, and the outcome: achieved, impossible, or cleared. The goal colour is violet throughout, so it never reads as working (amber), ask (pink), or elevated (amber).

Best

These build on B3 and keep today's layout recognisable. Each one puts the goal in a different place relative to the composer.

A1 · Dock+

best

B3's live header, with the goal as a second line inside it. Both status lines share one hairline-divided header, so the composer reads as a single object. The footer holds attach, the Harness & Model button, a one-tap effort meter, approvals, and send. Tap the goal line to open its receipt.

Goal lives
Header line 2, violet target, with a check count on the right.
Height cost
+22px while a goal is active. Nothing extra when none is set.
Effort
The meter chip cycles on tap: Low → Medium → High → Max. Try it.
Stop / send
Empty and working shows stop. Typing adds send (steer) next to it.
Strength
Closest to B3, which you liked. The why-not-yet reason is one tap away.
Risk
The header grows to 3 lines if subagent or drift banners also stack there.

A2 · Folder tabs

best

Goal and live status sit in two tabs on the composer's top edge: goal on the left, working on the right. They cost almost no height and read as labels on the composer rather than another bar. The Harness & Model button is split: the left half opens the picker, the right half cycles effort.

Goal lives
The left tab. It turns green with a receipt when the goal is met and red when it's impossible.
Height cost
+22px, whether or not a goal is set, because the status tab is always there.
Effort
The right half of the split button. The picker still has the full list.
Strength
It looks distinctive, and the outcome stays visible after the run ends.

At 390px the goal text truncates hard. Tabs also need care in light mode.

A3 · Status island

best

The status leaves the composer and floats above it as a black pill, like the iPhone's Dynamic Island. It shows the timer and the goal's check count. Tap it and it grows into a live card with the step, goal, reason, stop, and clear. The composer shrinks to a one-line capsule with icon-only effort, approvals, and harness.

Goal lives
In the island: a check count at rest, the full card on tap.
Height cost
0px. The island floats over the transcript's bottom fade.
Effort / approvals
Icon-only: the meter bars and the shield, amber when elevated. Desktop shows labels.
Strength
The most room for the transcript on a phone, and it feels premium and native.

The island covers the last line of the transcript. Icon-only approvals are less legible for new users.

A4 · Meta line

best

A calm, pro-tool look. The composer is only the text field, attach, and send. Status and goal read like plain text above it, and every setting reads like plain text below it: opus-5 · high · ask · 42%. Each word is its own tap target, which suits a monospace UI and sits closest to a terminal prompt.

Goal lives
Plain text above the composer. A violet "goal" token below it opens the receipt. With no goal, the token reads "+ goal".
Height cost
+18px per live line and +26px for the meta line.
Effort

Strength
The densest and most honest layout: every setting is visible as text, with nothing hidden in icons.

Tap targets are words, and some are under 44px tall. The rows need padding to be thumb-safe.

Middle

These go further from today's layout. Each one tests a single idea: a scrollable chip tray, a goal border, a pinned goal card, a keyboard toolbar, or moving the goal to the top bar.

B1 · Chip tray

middle

Every control is a labelled pill in one row you can swipe sideways, with send pinned at the end. The goal is the first pill when one is active. Nothing is icon-only and nothing needs a second tap to read. Attach opens a sheet of big tiles, and "Set goal" is one of them.

Goal lives
The first pill: 35/38 · 6. Tap it for the receipt. It isn't there when no goal is set.
Height cost
+20px status line. The tray replaces today's footer.
Strength
You can scan every label and it's easy to extend. Chips can be long-pressed to reorder or pin.
Risk
Chips past the fold (Attach here) are easy to miss, and horizontal scroll conflicts with the swipe-back gesture.

B2 · Goal border

middle

The footer is icon-dense: the effort bars sit inside the Harness & Model button and are their own tap target. Approvals is a shield with a tiny caption.

Goal lives
The composer's border and its label. Violet while pursuing, red when impossible, green for a moment when met.

+9px for the label.

Strongest ambient signal. The goal is part of the composer rather than a line beside it.

B3 · Pinned goal card

middle

The goal gets its own small card pinned above the composer, holding the condition, a pass-rate bar, and the checker's reason. Treat it as the mission and the composer as the conversation. When the keyboard opens, the card shrinks to a one-line pill so typing space wins.

Goal lives

When you tap to type, every control moves to a toolbar docked on the keyboard, the way iOS Notes and Things do it. Controls are there when your thumbs are down and gone when you're reading.

C4 · Goal as canvas

wild

The moment you type, it gets out of the way. This costs no extra space, because an empty composer is wasted space anyway. The right-hand phone shows setting a goal: typing /goal turns the composer violet and explains what will happen.

In the empty composer. Once you type, it drops to a one-line header like A1's.

C5 · Check timeline

wild

The goal shown as what it really is: a series of checks. Each dot is one turn the checker judged. The pulsing violet one is the check that's coming. Tap any dot to read that check's reason. It shows momentum at a glance, so you can see whether the reasons are converging or going in circles.

Goal lives
A timeline above the composer, collapsing to its first/last dots past 8 checks.
Height cost
+60px with the reason bubble, +26px without.
Needs
Each check's reason kept, not just last_reason. Conduit would store every active_goal event, which suits the event store.
Risk
The most data-hungry design, and it's noisy for goals that finish in 1–2 checks.

Shared

These pieces work with any design above: the Harness & Model picker, every state a goal can be in, and OpenCode support.

Harness & Model picker

shared

One button, showing the harness logo and model name, holds everything we're removing from the input row: harness (including custom instances), model, effort, context window, and agent. Effort stays in here as well as in the quick chip. Three layouts:

P1
Everything is one tap away, with no back button. Recommended for phone. It fits in about 480px.
P2
Scales best if the model list grows long (OpenCode lists every provider's models). The cost is two taps per change.
P3
The desktop version of P1, usable entirely from the keyboard. On OpenCode, the middle column groups models by provider.
Button label
Logo plus model name only. Show context size (1M) as small grey text on desktop, and drop it on phone.

Goal lifecycle

shared

Every state a Claude goal can be in, drawn in A1's header style, though any design can use the same set. Violet means active, green means met, red means impossible, and amber means paused. The goal line never grows beyond one line plus an optional reason line, so the composer's height stays predictable.

Source
Claude sends active_goal with the goal or null. Conduit derives checking (turn ended, no update yet) and achieved/impossible (goal went null right after a reason) from the order of events.
Undo
Re-sends /goal <same condition>. The check count restarts; say so in the toast.
Paused
Claude has no pause command, only an automatic pause when an error happens. If the user asks, we could add a manual pause that clears the goal and remembers the condition (Codex has this).
Risk
active_goal isn't in the public SDK message type. Before building, confirm it actually reaches query() consumers in 0.3.280.

OpenCode support

shared

OpenCode has no goal feature (there's an open request, anomalyco/opencode#27167, and a few community plugins). The composer is identical apart from the cyan logo. The question is what happens in the goal slot.

(a) Not supported
Show "Set goal" greyed out with "Claude only", and treat /goal as an unknown command. Ships with v1 at no cost.
(b) Conduit-run goal
Conduit stores the condition. When the session goes idle, a cheap model call judges the transcript and returns not yet, met, or impossible. On "not yet", conduit sends "Continue toward the goal: …" as the next message. The small conduit tag shows who is checking. This works for any harness, and could later replace Claude's built-in goal if we wanted identical behaviour everywhere.
(c) Community plugin
Detect a goal plugin and read its state. That ties us to someone else's format, which could change without warning. Not recommended.
Recommendation
(a) for v1, (b) as a follow-up. (b) is a real feature: it needs a loop owner, a token budget, a stop condition, and a way to survive a daemon restart. It should get its own spec, not ride along with the redesign.

Recommendation

pick

A1 Dock+ as the base, plus four pieces taken from other designs. It keeps the B3 status line you liked, adds just one line (22px) and only while a goal is active, and every control is still a single tap on phone and desktop.

Base: A1
B3's status line, the goal on line 2, and tapping the goal opens the goal details (Edit / Clear). Footer: + · logo + model · effort meter (tap to cycle) · approvals shield · send/stop.
+ B1's attach sheet
The + button opens photo, camera, file, and Set goal, so goals can be found without knowing /goal.
+ C4's set-goal flow
Typing /goal turns the send button violet and shows a one-card explainer.
+ C5's check history
Put the check timeline inside the goal details, not as a permanent rail. You get the full history without paying for the height.
+ A4's approvals menu
Each mode gets a one-line description, and elevated modes stay amber.
Picker
P1 sheet on phone, P3 popover on desktop, both built from the same parts.
Removed
AgentSelector and ContextWindowSelector leave the input row and move into the picker. The context meter stays in ContextBar.
Runner-up
B2 goal border, if you'd rather the goal be ambient (a violet frame) than a line of text. Its downside: a border can't show the reason text.
