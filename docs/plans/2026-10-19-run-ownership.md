# Provider run ownership

Each committed `send_turn` reserves a fresh conduit run id in the outbox `run_id` column and a `provider_runs` row. A run has `id`, `session_id`, `status`, `requested_at`, `started_at`, `completed_at`, and `joined_into`. Status is pending, running, completed, error, interrupted, or joined. A joined reservation names its effective run in `joined_into`; failure, recovery, and command completion read that column instead of reconstructing membership from event JSON. `turns.run_id` records membership at stamped user-message placement; `turns.started_at` records provider acceptance separately from membership, message parents, and input ids. Runtime and stored event envelopes carry optional `runId`; projectors read this field, so it is persisted metadata with a consumer.

The outbox transaction reserves the initial run before execution, retaining busy and exact processing-timeout ownership before claim. Recommitting an unclaimed command reuses its still-live reservation rather than interrupting and replacing it. A new handoff after an end reserves a fresh initial owner so its timeout and busy state exist before claim; retries of the existing outbox row replace an ended reservation at claim. The running-claim rejection and idle outbox-row replacement remain necessary to preserve exclusive command execution and command history. Run rows are created only by projection, not the command repository. Claude carries that reservation through runner input and replay. Its `command_lifecycle.started` frame emits `run.started` with the accepted input id and reserved run id. If a root run is still active, the input joins it and its unused reservation becomes joined. After a terminal result, the next started frame uses its own reservation. An exact Claude native result arriving before intake selects its matching pending reservation context before usage-limit interception and terminal translation, without emitting acceptance; an unrelated active input retains its context and accounting ledger. A result that explicitly covers several inputs translates shared output and accounting once, then emits bare terminal facts for the other exact reservations through the same terminal predicate and projector. This does not manufacture started frames. A delayed OpenCode echo of an already-ended send retains its exact reserved or accepted run and inherits that run's recorded terminal state and time, without reopening it. Queueing and sending never join a turn. All translated root output uses the resolved run; terminal output retains that run even while later input waits. Delayed output with a known message or tool owner retains that original run; output whose owner cannot be resolved stays unplaced. OpenCode assistant errors resolve through their native message or parent input; an unknown assistant owner stays unowned, while message-less session errors can use the active run. OpenCode accepts a local input only from its exact reserved native message id; unrelated native echoes never consume a local reservation. It uses that matching user-message echo as its input acceptance acknowledgement, retains message-to-run ownership for subsequent output, and treats session idle/error as the root terminal boundary. `emitsMessageParentIds` continues to link assistant messages to inputs. An external OpenCode input has no local outbox commit; its live native user echo is explicit acceptance and allocates a conduit run there. A reserved local id with no matching command, a REST snapshot, or an unplaceable signal cannot create an observed run.

OpenCode summarize is synchronous but does not accept or return a caller-owned message id. While its RPC is outstanding, a narrow bridge pairs the first new native compaction part with that local input, one-to-one. Ordinary unknown user echoes remain unattributed. Overlapping RPCs retain their separate bindings until they return; repeated parts cannot consume a later command. Before translation can use that bridge, ingress checks the native message's durable `input_id`; an already attributed marker is a repeat even after reconnect clears announcements. Native assistant errors/finishes and idle still decide the outcome, never summarize returning true. Accepted ambiguity: an external compaction started in the same session while our summarize call is outstanding can be attributed to ours. Session-wide error settlement retains the original translated batch, including its compaction failure notice, through the same terminal predicate.

External native OpenCode echoes reuse their exact recorded acceptance on reconnect. A newly observed external input joins the sole running run or starts a fresh conduit run at acceptance; its native message id identifies that acceptance without creating a local `messages.input_id`. Only live SSE user echoes establish this ownership, never historical backfill.

`run.started` activates the resolved run, stamps the accepted input's `started_at`, and rewrites all members of a joined reservation to the effective run. A continuation carries an explicit user-message reference to the cut-off turn; it never selects an input by age. Only a terminal event stamped with that run closes all member turns, including inputs placed before intake. Starting another input or reply, an unowned busy/idle signal, and provider message ids cannot close them. Duplicate terminal events do not close a run again. Known-run usage or model corrections may still update accounting without moving its terminal boundary. The shell completion identity also comes from placed run membership, in the terminal transition transaction. A reservation that fails before placement cannot erase another run’s completion boundary. Unowned terminal events and stale owned events cannot advance shell completion or settle children. Usage corrections attach only to the explicitly named input or reply owner; completion still closes every run member. Historical REST snapshots retain their historical display projection without deciding live run completion. Inherited fork terminal facts preserve historical attention only; they cannot change runtime completion identity, status, child sessions, or live turn state. Existing legacy attention remains durable baseline data when no run ownership can be reconstructed.

Membership exists before intake, so an owned error or interruption closes the placed input through its reservation without inventing acceptance. There is no terminal userMessageId exception. The run transition also closes its member messages' streaming/thinking state and interruption markers; an adapter's retained message identity cannot decide that cleanup. Failure cleanup may place an input after its reservation ended; the stamped placement inherits that exact run's outcome and time. Fresh retry placement moves a reused turn from its ended owner to the attempt's live reservation. Late duplicate placement cannot replace a newer active owner.

Inbox busy and error/interruption pause read the latest effective run status, resolving joined_into. Pending/running is busy; error/interrupted pauses queued work until explicit resume/reset. Turn display state, approvals, and adapter activity do not decide busy. Both inbox readers share the same run selection and pause predicate, including reset ordering and failed requeues, prioritizing an outstanding run over newer ended work; an unrelated native run’s completion cannot hide an indeterminate reservation. The error/interruption pause calculation remains independent of that ordering. A reservation whose exact command records routine `steer-declined` delivery has returned its input to the inbox, so it cannot replace the active work or pause the returned queue; actual Stop/error reservations remain eligible. Failed queue admission before a reservation exists creates its reservation, stamped placement, and terminal through the same event projection path.

Stage 1 centralizes the end decision in `runTerminalStatus` in the turn projector. Claude and Cursor `turn.completed`, any provider's owned error/interruption, and OpenCode session idle/error can end a run. OpenCode's per-message `turn.completed` only contributes accounting; a finished tool-call step cannot end the run or its command. An unowned session-status observation may update an orphaned session row only if no run is pending or running; it changes neither attention nor run, turn, outbox, or receipt state. Runner recovery, confirmed session-wide settlement, intake fallback classification, and relay alerts use that same decision.

OpenCode startup command recovery classifies its guarded provider-status proof through `runTerminalStatus`. Success also requires the command's accepted run and its final exact-parent reply to have a successful loop finish, following [OpenCode's loop rule](https://github.com/anomalyco/opencode/blob/v1.19.1/packages/opencode/src/session/prompt.ts#L1054-L1059): a finish other than `tool-calls` or `unknown`, with no reply error. A message completion timestamp alone cannot prove a successful run; neither can idle with unfinished history.

The turn projector owns terminal transitions and settles matching `send_turn` outbox rows and receipts immediately in the same transaction. It includes reservations joined into the ended run, preserves exact outbox attempt identity, and takes retryability and provider-handled retry information from the terminal event. A late accepted join inherits the recorded run end and settles its command from that same exact terminal fact. This lives in projection rather than an adapter callback so replay, runner exit, and ordinary provider output cannot diverge. Adapter return values no longer write send command outcomes. Cursor includes its existing retryHandled policy in terminal error data; the command cannot recover that policy from a returned result. Successful Cursor run terminals rely on run membership for completion and their exact answer message for accounting, omitting the prompt-only userMessageId marker. Transport and admission failures fail through the typed error channel, which produces an owned failed-delivery event; ordinary lifecycle results already have provider events. The background drain's running claim remains until projection ends its run. Non-send commands retain their own command outcomes.

Projection reports the event ids that actually ended runs through a transaction-local set. Relay done/error alerts and automatic turn recaps use this committed report; duplicate facts and rollback emit no lifecycle alert. Terminal events also carry the provider state updates consumed for native resume/accounting, saved by the projector in the same transaction as the run, turn, outbox, and receipt changes.

Stage 2 stores the current reservation in `provider_command_outbox.run_id`. Its claim UPDATE retains a live pending/running reservation or assigns a fresh id when the old reservation ended or is absent. The claim, `run.requested` append, and projection commit together through `CommitAndSignal.write`; a losing claim creates nothing, and a failed projection rolls back the claim. Projection of the new request clears the prior receipt failure while that claim is running, so concurrent waiters observe the current attempt. Execution and runner replay carry the returned column id, never payload JSON ownership. Reservations are never reopened. Failure cleanup uses the captured claim id rather than re-reading a later attempt; malformed payloads still fail that known reservation. A recommit with no new events preserves the command projection cursor. Stamped retry placement moves a reused input from its ended prior owner to the fresh reservation; intake only marks acceptance. The terminal event carries a configured retry deadline when needed, so projection retains the existing deterministic backoff without another outcome writer.

Command completion and provider intake are separate facts. Claude/Cursor sends return an intake acknowledgement at run.started, or a pre-intake terminal/failure; the wrapper's sendsInFlight counter and eager placement/busy synthesis are deleted, and native payloads stamp their own placement with the requested reservation; native execution and retained output sinks continue in their existing scope. OpenCode waits for its captured reservation's durable intake, join, or pre-intake end after prompt_async dispatch. There are no pendingTurns completion Deferreds, terminal matching snapshots, per-session success broadcasts, or terminal send barriers. Foreground execution races durable receipt polling against intake delivery. The executor bounds intake by the processing deadline and allows at most one second for a local recall acknowledgement. Recall can remove only an input still in Conduit’s queue; SDK handoff or prompt_async submission is not acceptance. A recalled input fails its reservation through an owned terminal. Otherwise the outbox stays running and the receipt stays requested, both carrying delivery_indeterminate in their existing error_code field. The bounded response is indeterminate, without a failure; the pending reservation has no started_at and continues to keep the inbox busy. Both foreground claim and background ordering block later sends while this attempt remains open. No native proof polling, automatic native cancellation, retry loop, or held admission semaphore is involved. Real acceptance remains registered and can later attach the input to its actual run; its owned terminal clears the marker through normal projection. A failed receipt is returned as its recorded error/interruption acknowledgement after bounded local recall, not a second execution failure. Foreground cleanup may restore a missing input or its queue position, but emits no second terminal. Handoff bookkeeping after intake logs persistence failure without changing provider lifecycle; a later handoff may resend context that could not be recorded. Adapter acknowledgements never settle outbox rows; the background drain's running row remains until projection ends its run.

Indeterminate delivery is never automatically resubmitted, including command replay and runner adoption after daemon restart. Recovery restores native event sinks independently, so later native acceptance and terminals still project; confirmed runner death and guarded OpenCode startup recovery retain their existing owned settlement paths. Native cancellation follows explicit user actions and the usage-limit failover exception below. Stop snapshots its claimed run cohort in the same transaction that returns unclaimed handoffs. OpenCode Stop settles only that snapshot after native abort returns; a concurrent Resume can claim a fresh reservation after the existing five-second barrier without that late confirmation ending it. Cohort idle facts carry the same exact owners, so the projector also preserves a later run's visible busy state. Stop atomically returns unclaimed handoffs to the inbox before native cancellation. Their unused reservations receive owned interruptions, so projection settles their outbox rows and receipts; Resume reserves a fresh run without reopening the old one. A runner session with indeterminate delivery uses the existing explicit end_session command before confirmed session-wide settlement, because ordinary Claude interrupt deliberately keeps a pending steer alive. Normal closed admission keeps inputs in the inbox. A committed handoff can also wait as an unclaimed pending outbox row behind an indeterminate command or across a crash; that interval has no fixed upper bound. Stop therefore uses the existing input.requeued path (option b), returning these rows in their retained inbox admission order. The return event carries its exact immutable run owner, including joined reservations, so projection replay survives outbox retirement. A scheduled retry already has an ended run and failed receipt; Stop withdraws its retry queue row as recommit would, rather than ending that run again or leaving a stale ordering head. The reactor claim and drain rules remain unchanged. Old foreground cleanup recognizes any returned handoff and cannot synthesize a placement that consumes it again; immediate Resume waits for that old live claim to unwind, then re-enters command deduplication so concurrent Resume requests share one fresh attempt. Interruption/error keeps the returned queue paused until explicit Resume. If native acceptance and terminal never arrive and the provider remains live, Stop is the visible way to resolve an indeterminate reservation; no automatic retry risks a duplicate send.

Every accepted or silent Stop worker retires only its snapshotted claimed cohort at the 30-second bound if native termination has not arrived, including a plain Stop later joined by Run now. A rejected interrupt fails visibly and never retires that cohort. A retained Claude query closes the captured run ids to new membership without losing their exact output owners; a pending steer accepted afterwards uses its own reservation. Membership stays closed even if a late interrupt acknowledgement rejects, because the daemon may already have retired the cohort; that rejection itself still settles nothing. Later native results retain their accepted input owners and cannot reset a replacement run.

Explicit contract exceptions: E1. Automatic usage-limit failover may end the native session after the provider reports the limit, either a rejected rate-limit frame or a limit result. This is the established failover feature, not cancellation of live work. E2. Ordinary Claude Stop keeps a pending steer alive and answers it afterwards, as on main and covered by the Stop-with-a-steer regression.

A surviving pre-upgrade runner cannot stamp a new run id. Its successful replay therefore emits an owned completion for only the exact migration-authored reservation carried by that command. Projection atomically settles that reservation and its command. The shared terminal predicate recognizes both completed and joined replay results. This compatibility completion does not emit acceptance; the migration supplies exact input membership before recovery. Ordinary unowned modern output never acquires this authority.

Runners announce `stampsRunIds: true` in their existing hello. A retained runner without it requires replacement even when build ids match, and holds input admission until then; the inbox counts this fence as busy. Queued sends and steers stay in the inbox, and direct outbox sends stay unclaimed outside their intake deadline. Recovery may reattach an exact command already in the old runner’s send journal, but returns provably unreceived running attempts to pending, preserving their reservation and attempt fence. The reactor subscribes to admission changes before rechecking the hold and claims only after retirement; no process-runner send waits for a swap. A claim racing adoption returns to that same pending path. If the hello omits its journal, recovered delivery stays durably indeterminate and is never replayed. Recovery captures those exact reservations, including a marker retained across another daemon restart. Eviction settles only that captured cohort through the existing owned error settlement with the message "Delivery could not be confirmed across the upgrade"; admission stays held until the terminal events commit. Stop remains available while native work is active. New-runner intake remains an accepted, non-terminal result through the existing completion predicate. Legacy runners always retire through end-session restart at quiescence, including idle adoption, even when a settings snapshot would allow warming. A single pre-upgrade hook diverts them before make-before-break eligibility; modern runner upgrades remain unchanged. Restart uses the existing startup deadline and bounded process cleanup. Rejection or timeout logs one warning with the session, runner and build identities independently of cleanup guards; the next input can start a fresh runner or report the ordinary visible startup failure. After a successful explicit Stop settles its claimed cohort, a held legacy runner restarts even if the native query never becomes quiescent. Stop, approvals, questions and task Stop bypass the input fence. One adoption and one retirement log name the session, runner and build. This compatibility hold uses the existing inbox, outbox and terminal settlement.

Failure settlement carries the exact failed reservation cohort, independent of turn acceptance. Runner ownership is retained after intake acknowledgement clears its transport send journal, and stale runner generations/attempts remain fenced. Native activity, rather than adapter reply lifetime, holds runner retirement, retuning, and shutdown-after-turn. Durable output acknowledgements recheck retirement after sink release, so an intake acknowledgement cannot strand a retiring controller. Native output persistence failure retires the affected runner so confirmed process-exit settlement can recover the still-outstanding runs.

The reactor alone re-places a hidden continuation’s existing cut-off message header with the current claim before provider intake, and each retry repeats that fact for its fresh reservation. Normal retry placement reuses the existing body while projecting only a changed membership header. Message text and its original creation time are unchanged; intake selects only an already-member cut-off turn.

Foreground commands keep the existing direct outbox claim and may reach an active provider run, including several steers before any intake acknowledgement. Delivery does not join them to the run; each input still waits for its own provider intake event. There is no foreground run-status fence or intake-dependent steering exception. The inbox treats main’s in-memory Stop and account-switch fences, or any pending/running reservation, as busy. A bound Stop for Run now snapshots the same claimed cohort as ordinary Stop; its 30-second retirement uses the same owned settlement and cannot consume a later claim. Its queued replacement retains input.interrupt_requested priority and bypasses the interruption pause. Ordinary Stop retains the pause and returns unclaimed sends to the inbox. A rejected native interrupt leaves the claimed runs open and reports the failure. The v6co.3 background drain retains its original per-session ordering and live-command exclusion. Upgrade keeps a legacy executing command busy by giving its reservation running status, and the existing runner recovery settles that exact reservation with owned events.

Conduit failures require an explicit run or input owner. Delayed processing, continuation, and prompt-response callbacks capture their reservation or the exact asked event's run before arming; acceptance persists the effective owner in `joined_into`. They never look up a reused turn's current run when firing. A terminal owner's late response or acknowledgement cannot replace the newer run's processing timer. Processing and post-answer timeouts never prove termination. For an accepted, still-running exact owner they append a non-terminal `turn.notice` with the ordinary or continuation silence copy. Projection checks ownership again in its transaction, stores a standalone text part with notice metadata, and the existing informational transcript component renders it across reload. No run, turn, command, receipt, or session status ends. A fired callback remains available for activity to re-arm; silence alone produces only one notice. Native terminals and Stop clear that callback. Unaccepted delivery remains the executor’s bounded intake responsibility. Immediate failures before a reservation exists retain their exact input id.

`settleSessionRuns` is the explicit session-wide end path. A fresh provider idle/stopped status, a confirmed process exit, or a provider session-scoped failure authorizes it to enumerate outstanding provider-owned run ids and write an owned interruption/error for each, with a reason. Known native successful ends are retained; unresolved outcomes become interruptions, never invented successes. A local reservation still awaiting intake remains owned by its outbox command, even if delivery has returned: an earlier run's idle/error cannot consume that future input. Exact command failure/recovery settles such a reservation. A confirmed runner exit supplies the failed process's exact command-attempt and accepted-run cohort, checked under the admission lock before releasing a replacement; later reservations survive. Interruption reasons are event data, rather than unused event metadata. Ordinary unowned per-run terminals still cannot close a turn. Duplicate confirmation cannot close an already-ended run again. Queued inputs retain the existing pause after interruption/error and can be resumed explicitly.

Runner exit settlement first acquires the same output queue used by native events and scoped runner failures. A native terminal already being committed wins before synthetic exit settlement checks the run state, preventing both a false failure and duplicate owned failure events. An idle runner's rejected, unaccepted send retains its reservation for retry on the replacement runner.

Startup enumerates outstanding accepted OpenCode runs independently of command status, including native inputs with no outbox row and local inputs whose command completed just before its owned idle committed. It probes the bound provider without starting one, checks session binding, event-store sequence, live-ingress revision, and reconnect generation, then uses the session-wide end path when the provider confirms idle/stopped. The current-input guard accepts any member of the same run. Recovery of a lost echo stamps the command's reservation on its existing placement event; membership projection precedes the REST display guard and does not invent intake. Busy or unavailable responses preserve the run and retry against the frozen startup candidates. Native input acceptance invalidates reconciled idle proofs immediately, before persistence, so a sampled idle cannot end newly accepted work. Recovery and the outbox drain run before inbox startup.

First native sighting persists its directory in `session.created` metadata. `SessionWorkspace.get` reads that fact for startup probes and subsequent sends until an explicit workspace move or reset overrides it. An omitted status alone is not idle confirmation: startup validates that the native session still exists with the same id in the probed directory before normalizing omission to idle. After an explicit persisted workspace move or reset, the native detail can retain its creation directory. A non-branch-rename workspace event preserves this authority even when a reset clears the workspace column. That mismatch requires both the stored workspace and native directory to be non-busy, with native identity/directory rechecked after the additional read. A busy/retrying native scope or changed detail preserves the run. A native-only/default directory mismatch remains unconfirmed. All reads share the existing event/revision/generation commit guards. No extra migration is needed for these safeguards; migration 0075 is the new ownership migration and shipped migrations remain immutable.

A confirmed OpenCode instance stop settles accepted runs and exact durable running outbox claims, including reservations awaiting intake. Earlier idle/error for run A cannot consume an unrelated unaccepted reservation B. Pending or retryable commands that were never claimed remain available to the drain; no waiter snapshot supplies authority.

Cursor is also an active local runner. Its initial acceptance is the SDK's `RUNNING` stream frame matching the returned native run id and agent id; SDK 1.0.37 emits this after `markRunStarting`, separately from returning a send handle. A delivered steer acknowledgement (`complete_delivered`) or its uniquely matching appended-user delta accepts that input into the same conduit run; repeated prompt text waits for its exact acknowledgement. Each foreground translator retains that conduit owner through its terminal event, while native run references remain separate. The adapter must reject foreign run frames, avoid accepting an input at send time, preserve separate ownership after a terminal, settle pre-acceptance failures without claiming intake, and leave child output outside the foreground run. A pre-intake failure ends the reserved run and its command, releases inbox busy, and closes its member input while leaving started_at null. Its daemon tests observe that exact failure and a successful subsequent input. Recorded-event tests exercise these boundaries through the session runner.

Migration 0075 follows main's shipped 0074_turn_recaps migration. Main's 0069_goal_check_metadata through 0074_turn_recaps remain unchanged. It adds the run table, including joined_into, the turn ownership column, and the current outbox run_id column. Stages 1 and 2 folded these columns into the unreleased ownership migration, and upgrade compatibility (82tn.31.1) added exact command-to-turn membership there. The main merge renumbered that migration from 0069 to 0075 without changing its SQL. Shipped migrations and the legacy pre-upgrade runner completion path remain unchanged. Historical completed turns retain null run ownership; no owner is invented from recency. The daemon store importer copies the run table and remaps its references together with session and turn ids. A session-deletion trigger removes its reservations. Existing pending and retryable outbox sends receive stable pending reservations during migration. A legacy running send receives a running reservation with its carried run id and start time, so inbox busy remains true until existing runner recovery writes its owned terminal event. Upgrade does not synthesize a terminal for that executing reservation. Existing open turns join their recoverable send command through the exact continuation cut-off or input/user-message identity, including the user message’s stored input_id. Migration changes only their run_id: state, started_at and completed_at stay intact. Only open turns without a recoverable owning command are interrupted. Ordinary runner and OpenCode startup recovery then decide the linked run’s outcome; no new recovery outcome logic is needed. Surviving legacy runner output without a carried run id remains unplaced. The migration reads legacy payload runId once to backfill the outbox column; all runtime ownership reads use the column. Pending reservations resume with the carried id, and a later claim replaces an ended reservation atomically. Repeated migration-ledger repair skips upgrade settlement once the ownership column already exists.

Normal startup recovery preserves materialized legacy turn outcomes. A replay into empty read-model tables cannot recover those outcomes from old unowned terminal events: it leaves those turns unowned and pending. The upgrade's exact membership and orphan interruption are also materialized state, so exact parity for a future destructive rebuild requires a separate durable legacy baseline rather than guessed run ownership.
